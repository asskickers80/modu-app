## 0. 먼저 짚을 것: 이 프로젝트는 이미 웹입니다

네이티브 모바일 앱(iOS/Android)은 존재하지 않습니다. 현재 산출물은 **브라우저에서 도는 웹앱을
모바일 화면 비율(430px)에 맞춰 만든 것**이고, PC에서 열면 화면 가운데 430px 기둥으로 보입니다
(`src/App.jsx:71-73`). 폰에서 쓰는 것도 모바일 브라우저 접속입니다.

따라서 "웹 버전으로 확장"은 두 가지 뜻이 될 수 있습니다 — 8절에서 둘 다 다룹니다.

## 3. 폴더 구조

```
src/
  screens/      화면 1개 = 파일 1개
                A=온보딩·홈, E1=매물등록(양도인), E1p=상가등록(임대인),
                E1b=기업회원, E2/E2L=상세, D4=메시지, A7=축별 대시보드
  components/   공용 UI (카드·바텀시트·칩·헤더)
  lib/          도메인 로직 — 화면과 분리된 순수 계층
  hooks/        4개 (프로필 라우트 동기화·스와이프 전환·안전한 뒤로가기·토스트)
  contexts/     AuthContext 1개
api/            Vercel 서버리스 (OAuth 토큰교환·공공데이터 프록시·크론 배치)
```

**핵심 설계**: `lib/`가 화면에서 분리돼 있습니다. 매출 분석, 완성도 점수, 문의 주제 분류,
주소 파싱, 건축물대장 조회 같은 계산 로직이 화면 코드에 섞이지 않고 독립 모듈로 존재합니다.
이것이 이식·확장 시 가장 큰 자산입니다.

## 6. 인증 방식

Supabase 기본 소셜 프로바이더를 **쓰지 않고 직접 구현**했습니다. 카카오/네이버에서 받은
사용자 정보로 내부 이메일 계정을 만들어 Supabase 이메일·비밀번호 인증에 얹는 방식입니다
(`src/screens/AuthKakaoCallbackPage.jsx:139-150`).

브라우저에서 OAuth 토큰 교환이 CORS로 막히기 때문에, 프로덕션은 `api/kakao-auth`·
`api/naver-auth` 서버 함수를, 개발은 Vite 프록시(`/kauth`·`/kapi`·`/nid`·`/napi`)를 씁니다.

### 신원 모델 (이 프로젝트에서 가장 중요한 구조)

> 모든 데이터(매물·대화·매출)는 **기기 ID 기준**으로 저장된다.
> 로그인하면 계정에 묶인 기기 ID로 동기화·병합된다.

즉 **로그인 없이도 앱이 온전히 동작**하고, 나중에 로그인하면 그동안 만든 데이터가 계정으로
합쳐집니다. 진입 장벽을 없앤 대신 구조가 복잡해진 트레이드오프이며,
`lib/auth.js`의 `finishLogin()` 한 곳이 이 병합의 단일 관문입니다.

## 7. 상태관리 — 라이브러리 0개

Redux·Zustand·React Query 등 상태관리 라이브러리를 전혀 쓰지 않습니다.

| 무엇을 | 어디에 |
|---|---|
| 로그인 세션 | `AuthContext` (React Context 1개) |
| 프로필·역할 | `localStorage` 7개 키 (`modu_device_id`, `modu_profiles` 등) |
| 등록 폼 진행 상태 | `E1Context`/`E1pContext` (라우트를 감싸는 Provider) |
| 서버 데이터 | 각 화면이 `useEffect`로 직접 조회 |

- **장점**: 가볍고 단순, 의존성 없음
- **약점**: 서버 데이터 캐싱·재검증이 없어 화면마다 같은 데이터를 다시 조회.
  규모가 커지면 가장 먼저 손봐야 할 지점.

## 9. 웹 버전 확장 시 재사용 분석

### 시나리오 A — PC·데스크톱 대응 (이미 웹이므로 자연스러운 확장)

**재사용률 95% 이상.** 서버·DB·API·인증·도메인 로직 전부 그대로 유지됩니다.

| 그대로 재사용 | 손봐야 할 것 |
|---|---|
| `lib/` 50개 전부 | `App.jsx`의 430px 고정 틀 → 반응형 그리드 |
| `api/` 12개 전부 | 하단 5탭 네비 → PC 사이드바 (11개 화면에 복제돼 있음) |
| DB 16 테이블·인증 전부 | 바텀시트 UI → 모달·팝오버 |
| 타이포 토큰 17종·카테고리 색 | 목록 화면을 2~3열 배치로 |

**작업량**: 화면 59개 중 목록·상세형 20~30개가 실질 대상. 나머지는 폭만 늘리면 됩니다.
Tailwind를 쓰고 있어 `sm:`·`lg:` 접두사로 대응 가능한 구조입니다.

**선행 과제**: 하단 탭 네비게이션이 11개 화면에 각각 복제돼 있어, PC 레이아웃 도입 전에
공용 컴포넌트로 추출해야 합니다.

### 시나리오 B — 네이티브 앱(React Native) 확장

| 그대로 재사용 | 다시 만들어야 |
|---|---|
| **`lib/` 39개 (78%)** — 매출 분석, 완성도 점수, 주소 파싱, 문의 분류, 건축물대장 조회 등 순수 로직 | 화면 59개 + 컴포넌트 39개 (JSX·Tailwind는 RN 미지원) |
| `api/` 서버 함수 12개 전부 | 라우팅 (React Router → React Navigation) |
| DB·인증 모델 전부 (Supabase SDK는 RN 지원) | 테스트 96개 (Playwright → Detox) |
| 카테고리·지역·업종 분류 상수 | `localStorage` 7개 키 → AsyncStorage |

`lib/` 50개 중 브라우저 API를 쓰는 것은 11개뿐입니다
(`userProfile`, `auth`, `supabase`, `share`, `nearbyBrokers`, `authBackGuard`,
`unread`, `reviewLog`, `peerStats`, `appOrigin`, `kakao`).
이 파일들만 저장소·공유 방식을 교체하면 됩니다.

**결론**: 두뇌(로직·서버·DB)는 대부분 살고, 얼굴(화면)은 새로 그려야 합니다.
전체의 약 60~65%를 다시 만드는 규모입니다.
