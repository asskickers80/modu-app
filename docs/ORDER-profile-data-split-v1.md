# [ORDER-profile-data-split-v1] 축별 사업체 정보 분리 + 프로필 추가 시 승계 확인

■ 모드: 자율 판정. 멈춤 (a)스키마·마이그레이션 SQL (b)실DB 정정 (c)판정 불가만.
■ 장치 3(양도인 diff 요약) 의무.

## 배경·원칙 (대표 확정)
양도하려는 가게와 운영 관리하려는 가게, 소유한 상가는 서로 다를 수 있다. 축마다
자기 사업체 정보를 따로 가져야 한다. 단, 같은 가게라면 다시 입력하게 하지 않는다.

## 대상 축 (한정 — 그 외 축은 손대지 말 것)
양도인(seller) · 사장님(operating) · 임대인(landlord). 사업체·부동산 정보를 갖는 축만.
창업준비·기업회원·그냥구경은 현행 구조 유지 (희망 조건·회사 정보는 성격이 다름).

## 1. 데이터 구조 분리
- profile_data(서버)·modu_user_profile(로컬)의 사업체 관련 필드(category_main·
  category_sub·ksic_code·bizType·region·region_sub 등)를 대상 3축에 한해
  역할별 하위 객체로 분리. 구조 제안은 Code 판정 (예: profile_data.roleData.seller = {...}).
- 축 공통 정보(닉네임 등)는 분리하지 않고 단일 유지 — 무엇이 공통인지 목록화해 보고.
- 기존 데이터 마이그레이션: 현재 단일 필드 값을 어느 축으로 귀속시킬지 판정
  (현재 활성 축 또는 최초 온보딩 축) + 마이그레이션 SQL 제시 후 멈춤(a).

## 2. 프로필 추가 시 승계 확인
대상 3축 중 하나 이상을 이미 보유한 사람이 대상 축을 추가할 때, A3 질문 전에 확인:
- "기존에 등록하신 ○○(업종 · 지역)와 같은 가게인가요?" — 칩 2택
  [같은 가게예요 / 다른 가게예요]
- 같음 → 해당 축에 기존 정보 복사, 업종·지역 질문 건너뛰고 나머지 질문만 진행
  (건너뛴 값은 나중에 수정 가능)
- 다름 → 기존대로 전체 질문
- 보유 축이 2개 이상이면 어느 것과 같은지 선택 가능하게 (칩 목록), 판정 자율.
- 대상 축이 아닌 프로필 추가에는 이 확인 미노출.

## 3. 읽기 정합
각 축 홈·헤더·완성도·개인화·소개글 생성이 자기 축 데이터를 읽도록 전수 정정.
어느 코드가 어느 축 데이터를 읽어야 하는지 대조표 작성. 누락 시 다른 축 값이
노출되는 사고가 나므로 전수 확인 필수.

## 테스트
축별 값 독립 저장(한 축 변경이 다른 축 무영향) / 승계 확인 분기(같음·다름) /
마이그레이션 후 기존 계정 정상 표시 / 대상 외 축 무영향. 전체 스위트.
