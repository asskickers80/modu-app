# [ORDER] 공공 API 키 서버 이관 + 계정 삭제·원장 분리

> 접수 2026-09-06 · 저장 지시: docs/ORDER-key-proxy-account-deletion.md

## 배경
서비스 시작 시점의 앱은 완전한 네이티브 앱이다. 앞으로 모든 설계 판단은 이 전제를 따른다.
네이티브 앱 번들은 웹보다 키 추출이 쉬우므로 공공 API 키의 브라우저 노출은 부채가 아니라 결함이다.
또한 앱스토어는 회원가입이 있는 앱에 "앱 안에서의 계정 완전 삭제"를 의무화한다.
이는 모두의 soft delete·원장 보존 원칙과 충돌하므로, 데이터가 거의 없는 지금 분리 설계를 잡는다.

## 작업 A — 공공 API 키 서버 이관 (Supabase Edge Functions)

Vercel이 아니라 Supabase Edge Functions를 쓴다. 네이티브 전환 시 Vercel은 웹 전용이 되므로 앱이 갈 곳이 없어진다.

A-1. 현재 브라우저에서 직접 호출 중인 외부 API를 전수 조사해 목록을 보고에 포함하라(파일·함수·키 환경변수명).
A-2. 다음 Edge Function을 만든다. 요청·응답 형태는 현재 호출부가 기대하는 것과 동일하게 유지해 호출부는 URL만 바뀌게 한다.
   - public-data : data.go.kr 계열 전부(국세청 사업자상태, 소진공 상권정보, 국토부 실거래, 건축HUB 건축물대장). 단일 키를 공유하므로 한 함수 안에서 경로 파라미터로 분기.
   - naver-search : 네이버 뉴스·검색
   - ncp-geo : NCP 서버 키가 필요한 호출(역지오코딩 등). 지도 렌더링용 Client ID는 도메인 제한이 걸리는 공개 값이므로 이관 대상이 아니다.
   - gemini : 콘텐츠 생성
A-3. 클라이언트에는 이 함수들을 부르는 단일 래퍼 모듈을 두고 모든 호출부가 그곳만 통과하게 한다. 직접 fetch가 남아 있으면 안 된다.
A-4. 전환 스위치: 환경변수 VITE_USE_EDGE_PROXY. 기본값 off(기존 경로 유지). 대표가 Supabase secrets 설정 완료를 통보하면 on으로 전환한다.
   secrets 미설정 상태에서 배포해도 기존 기능이 깨지지 않아야 한다.
A-5. 함수별 verify_jwt 설정을 스스로 판정하되(로그인 필요 화면에서만 쓰이는가, 비로그인 매물 상세에서도 쓰이는가) 판정 근거를 보고에 한 줄씩 남겨라.
A-6. 각 함수는 호출을 events 테이블에 기록한다(함수명·성공여부·응답시간). NCP·data.go.kr 이용량 상한 감시용이다.

## 작업 B — 계정 삭제와 원장 분리

원칙: 개인식별정보는 실제로 파기한다. 거래 사실은 식별자를 끊어 통계로만 남긴다. 연락처 보관은 별도 선택 동의를 받은 경우에만 가능하며, 이번 오더에서는 동의를 받는 자리까지만 만들고 실제 보관 이관 로직은 만들지 않는다(법률 검토 대기).

B-1. SQL은 docs/SQL-account-deletion.sql로 작성만 하고 실행하지 마라. 대표가 콘솔에서 직접 실행한다. 미실행 상태에서도 기존 기능이 깨지지 않게 배포하라.

B-2. 스키마
   - consents (user_id, consent_type, version, agreed_at, withdrawn_at)
     consent_type: terms(필수), privacy(필수), marketing_contact(선택 — 양도·창업 정보와 중개 서비스 안내 수신), retention_after_withdrawal(선택 — 탈퇴 후 연락처 보관)
     기존 등록 확인사항 동의(terms_version)와의 관계를 정리하라. 중복 저장소를 만들지 말 것.
   - deal_records — 비식별 거래 성사 원장. user_id·listing_id를 두지 않는다. 업종, 지역(구 단위까지만), 권리금 구간, 면적 구간, deal_channel, 성사일, listing_type.
     마감 흐름에서 "팔렸어요"를 고른 시점에 적재한다. 기존 final_price_band·deal_channel 설문값을 그대로 쓴다.
     지역을 동·번지까지 남기면 재식별이 가능해지므로 구 단위를 넘지 마라.
   - users/profiles에 deleted_at 추가.

B-3. 탈퇴 처리
   - 설정 화면에 계정 삭제 진입점을 만든다. 설정 화면이 없으면 만들어라.
   - 삭제 시: 이름·전화·이메일·카카오 식별자·프로필 사진을 파기(NULL 치환). 되돌릴 수 있는 형태로 다른 테이블에 옮기지 마라. 이것은 백업이 아니라 파기다.
   - 매물·상가는 기존 soft delete 규칙대로 status='deleted'.
   - 대화 내용은 남기고 발신자 표시만 "탈퇴한 사용자"로 바꾼다. 남은 상대방 화면이 비어버리면 안 된다.
   - 찜·이벤트 로그의 user_id는 익명 식별자로 치환한다.
   - 삭제 전 확인 화면에 무엇이 사라지고 무엇이 남는지 그대로 적어라. 모두 화법. 붙잡는 문구를 넣지 마라.

B-4. 회원가입·온보딩에 선택 동의 두 항목을 추가한다. 필수 동의와 시각적으로 구분하고, 미체크가 기본값이며, 체크하지 않아도 가입이 끝까지 진행되어야 한다. 끼워넣기 금지.

B-5. retained_contacts 테이블과 이관 배치는 만들지 마라. 법률 검토 전이다. 대신 docs/에 "탈퇴자 연락처 보관 — 법률 검토 대기" 항목을 남겨라.

# 추가 지시 (2026-09-06) — 작업 C·D

## 작업 C — 고아 사진 파일 (작업 B에 포함)

PhotoGrid가 선택 즉시 Storage에 업로드하므로 매물 행 없는 고아 파일이 계속 쌓이고 있다.
계정 삭제 시 "이 사용자의 파일"을 매물 기준으로만 찾으면 고아 파일이 누락되고, 이는 파기 누락이 된다.

C-1. 업로드 시 파일 경로 또는 메타데이터에 업로더 user_id(비로그인이면 device_id)와 업로드 시각이 남게 하라.
     이미 남고 있으면 현재 방식을 보고하고 넘어가라.
C-2. 계정 삭제 처리에 "매물에 연결되지 않은 파일"까지 포함하라.
C-3. 24시간 이상 매물에 연결되지 않은 파일을 정리하는 배치를 만들되, 작업 D가 들어가면 초안에 연결된 파일은 제외 대상이 된다. 이 점을 고려해 설계하라.

## 작업 D — E1 초안 서버 저장

알림 기능과 무관하게 지금 있는 결함이다. 카카오 로그인 왕복에서 입력이 유실되는 경로가 실제로 존재한다.
설계 판정은 아래 결정에 따르고, 나머지 세부는 자율 판정한다.

D-1. 저장 위치: listings 테이블에 status='draft'.
     별도 테이블을 만들지 마라. 게시 시 status만 바뀌므로 데이터 이동이 없다.
D-2. 노출 차단이 이 작업의 핵심 리스크다. 목록·검색·상세·완성도·홈 피드·통계 등 listings를 읽는 모든 경로에서 draft가 제외되는지 전수 확인하고, 확인한 경로 목록을 보고에 포함하라.
     특히 비로그인 anon key로 draft가 조회되지 않아야 한다. 별도 저장소인 웹(modu-web)이 같은 DB를 읽으므로, 여기가 새면 게시하지 않은 매물이 웹에 공개된다.
D-3. 저장 시점: 1단계(주소) 완료 시 최초 생성, 이후 단계 이동마다 갱신. 주소 없이는 만들지 않는다.
D-4. 비로그인 이탈: 초안을 device_id에 붙이고, finishLogin에서 user_id로 승계하라.
     finishLogin이 유일한 병합 지점이라는 기존 원칙을 지키고, 병합 지점을 다른 곳에 새로 만들지 마라.
D-5. sessionStorage draft는 제거하지 말고 서버 저장 실패 시의 대비책으로 남긴다. 서버가 진실의 원천이고 sessionStorage가 보조다. 둘이 다르면 서버를 따른다.
D-6. 이어하기 진입점: 양도인 홈에 "등록하던 매물" 표시. 문구는 모두 화법으로 사실만 적고 완성도 퍼센트를 넣지 마라(완성도는 게시 매물의 개념이다).
D-7. 수정 모드가 draft를 쓰지 않는 현재 설계(E1Context.jsx:83)는 그대로 둔다.
D-8. 초안 자동 만료는 이번에 만들지 마라. 별도 결정이다.

## 순서
A → B·C → D. D가 가장 크고 노출 사고 위험이 있으니 마지막에 하고, D-2 전수 확인 결과를 보고에 반드시 포함하라.
